# 独立审查

审查的价值在于"另一双眼睛"：换一个模型，用全新的上下文，只给读权限。在主上下文里切换角色自己复查，不算独立审查。

## 1. 什么时候审

- 标准档：审一轮。
- 高风险档：一直审到没有严重问题（P0 / P1）为止。
- 直接做档：不审，除非用户要求。
- 原型、验证脚本、纯文档：审一轮，一般问题（P2 / P3）只登记、不阻塞。
- 项目另有规定的，按项目规定执行。

## 2. 发起

把审查说明写成一个自包含的临时文件，内容包括：

- 需求和完成标准（给出 TASK 路径）
- 审查基准：工作目录、分支、base、HEAD、diff 范围（含未提交的改动）
- 已经跑过的验证和结果
- 项目的专项清单（如有，例如 `docs/CODE_REVIEW_CHECKLIST.md`）
- 对审查方的要求：只读、不改文件、不写 TASK、按第 3 节的格式输出

默认跨模型审查：Claude 执行的任务请 Codex 审；Codex 执行的任务用 Codex 原生的只读子 agent，或者请 Claude 审。Claude 调用 Codex 的方式：

```powershell
codex exec --ephemeral --sandbox read-only -m <model> -c model_reasoning_effort=high -C <worktree> -o <out.md> - < <brief.md>
```

审查放在后台跑，等待期间继续做别的事。审查前后各看一次 diff 涉及文件的 `git status`，确认审查方没有改动任何文件。

## 3. 输出格式

把下面的格式写进审查说明，要求审查方照此输出：

- 每条问题：`ID ｜ P0–P3 ｜ 文件:行 ｜ 问题与证据 ｜ 影响 ｜ 建议修法`
- 严重度：P0 阻止合并；P1 验收前必须修；P2 可以以后修；P3 可选
- 最后给结论 `Passed` 或 `Needs Fix`，并列出没覆盖到的风险

## 4. 处理审查意见

这一步由你判断，不要转给用户：

- 每条意见先对照代码和需求核实，确认是真问题再改。
- 有依据的问题就修。过度防御、超出范围、或与已确认决策冲突的意见可以不改，但要在 TASK 里逐条写一句理由。
- 相关的修改可以合在一起改，只跑受影响的验证即可。
- 需要复审时，只把修改的部分和上一轮问题的处理状态发给审查方。

## 5. 记录与汇报

- TASK 的"记录 / 审查"一栏写：审查基准（分支、base..HEAD）、结论、严重问题怎么处理的、不采纳的意见和理由、审查输出文件的路径。
- 跟用户汇报只说一句，例如："另一个模型审过了，修了 2 处，1 处没采纳（理由见任务记录）"。

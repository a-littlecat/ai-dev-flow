# ai-dev-flow v2 设计稿：从"流程守门"到"harness + 回路"

日期：2026-10-29 ｜ 状态：已在 `v2` 分支实施为 skill 2.0.0（第 5 节）

## 0. 一句话

v1 把质量押在**每一项都走完流程、每次合并都问人**上；业界跑得快的做法把质量押在**项目自带的验证能力、机械约束和每天的复盘**上，人从同步回路里撤出来，只管方向、品味和单向门。v2 按后者重组。

---

## 1. 调研：现在跑得最快的几种做法

### 1.1 magpie（yetone/magpie）：全 agent 写、审、合、发

来源：仓库的 `AGENTS.md`、`LESSONS.md`、`docs/code-standards.md`、提交记录（2026-10 抓取）。

- **规模**：2026-09-23 建库，到 10-29 有 5000+ 提交。单日最多 220 次提交、约 170 次发版（10-05）；稳定后一天 70–275 次提交、7–18 次发版。
- **全部由 agent 完成**：`LESSONS.md` 第一句就是 "magpie's code is written, reviewed, merged and released by agents"。仓库不收外部 PR，社区只在 Discord、X 和 issue 里报问题，由 agent 实现，并在提交信息里署上报告人。
- **直接在主干上推进，靠绿灯发版**：每个 tag 都要等全量测试绿了才打；客户端自动更新，所以敢**往前修**。10-05 那天约 40 个提交是在修当天或前一天发出去的问题，这个错误率被接受了。
- **证据写在提交信息里，不写进任务文件**：大提交的正文写清跑了什么、**亲手改坏了什么来证明测试真能抓到**、哪些没试过、在哪台机器（mac/linux/windows）上跑的。
- **每晚复盘**：把当天的提交过一遍，看哪些要返工、哪些不该合、哪些验证太薄，写进 `LESSONS.md`，每条带"Seen N 天"计数。**同一条在 3 个不同的日子被看到，就升级进 `code-standards.md`**，审查方逐条按它查。
- **子系统参考文档**：`docs/subsystems/` 每个子系统一页，写职责、运行路径、状态和约束。改动契约时同一个 PR 里更新；agent 动手前先读。
- **人做什么**：定产品方向、收反馈、偶尔拍板。

### 1.2 poteto（Lauren Tan，Cursor）/ pstack：先有信任，再上并行

来源：`cursor/plugins` 里的 pstack README、她的讲座和文章转述。她自报每月合并 2000–2500 个 PR。

- **先有信任，再上并行**：agent 没人盯着也能交出可用的东西之前，开 100 个云端 agent 只会得到"一堆垃圾 PR"。
- **纠错阶梯**：一个问题要修在尽量靠上的那一层：架构（让错误写法写不出来）> lint/编译器/CI > 规则/skill > 人工审查。**同一句指令要写第二遍时，就改成代码。**
- **验证 skill 就是"手、眼、地图"**：一个可复现的 CLI 负责启动应用、抓 trace 和堆快照，再加一份磁盘上的功能地图，写明每个功能从哪里进去。agent 有了这些就能自己验证，人不再是瓶颈。她认为这是最关键的基础设施。
- **可逆的事不问"要不要"**（never block on the human）：直接做，给出结果，人事后纠正。只有单向门才确认。
- **自动合并要有独立验证方签字**：多条验证通道并行，各自重跑门禁、在真实界面上证明行为、审 diff，而且不信 PR 描述。验证结论必须对应最终要合并的那个 head。建议先用 autopilot-stack（只摞好 PR，人来合），再升到 autopilot-full。
- **按角色选模型**：写代码交给 grok，判断和难题交给 opus。审查用 `interrogate`：几个模型一起尝试搞坏 diff，**只保留能跑出来证明的问题**。
- **没有规划类 skill**："the best spec is code"。另设"园丁"角色：盯着合并流里反复出现的坏味道，每拔一根草就变成一条规则。

### 1.3 OpenAI Harness Engineering（Codex 团队，2026-02）

- 5 个月、100 万行以上代码，零手写，人均每天 3.5→5–10 个 PR。口号："Humans steer. Agents execute."
- agent 失败时不去更用力地 prompt，而是问**缺了什么能力、上下文或结构**，把它补进仓库。
- `AGENTS.md` 只有约 100 行，是一份目录，指向更深的文档（核心信念、可靠性、技术债清单）。
- 反复出现的审查意见改成 lint。每个 PR 都有审查 agent，被要求**倾向于合并、P2 以下不提**；作者 agent 可以反驳。
- agent 能自己起本地的日志/指标/trace 栈；构建回路压到 1 分钟以内。
- **大部分人工审查发生在合并之后**。需要返工的 PR 直接丢掉 worktree、从头重来。由 Symphony 编排，每个 agent 领一张工单。

### 1.4 Cursor：self-driving codebases

- 几百个 agent 连续跑一周，峰值约每小时 1000 个提交。
- 失败过的方案：平级 agent 加锁文件；固定的规划→执行→裁判流水线；一个 agent 包揽所有职责；中心集成者（成了瓶颈，被移除）。
- 留下来的方案：**递归规划者 + 只做一件事的 worker + 逐级向上交接**；接受一个稳定的小错误率，发版前再走 green 分支加修补。
- "约束比指令有效"，比如"不留 TODO、不做半成品"。真正的瓶颈是磁盘 I/O，不是 token。

### 1.5 Anthropic 官方与 Claude Code 团队

- 官方 best practices 的核心是：**给 agent 一个能返回通过或失败的检查**。必须每次都发生的事放进 hook、deny 规则或 Stop hook；`CLAUDE.md` 只放指导性内容。"同一行加了 IMPORTANT 还被忽略，说明它该是 hook。"
- 用 `/goal` 给长时间运行定终止条件，`/code-review` 用全新的子 agent 审。**对照 spec 审，并且写明 skip style**，否则审查方总能挑出点什么，全改就会过度工程。
- Boris Cherny 把演进概括为"源代码 → agent → 回路"。实际手段是 auto mode、routines（定时或事件触发的云端 agent，负责盯 issue、看护 PR、修 CI、rebase）、agent view 管一组会话、手机远程操控。
- 验证要能"自己跑产品"：skill 让 Claude 启动应用、点界面、测边界、修了再测。单测和 lint 只是其中一部分。

### 1.6 Ralph loop / Gas Town

- Ralph：一个 bash 循环，把输出和报错反复喂回去，直到达成目标。难点是上下文腐烂和失忆，所以状态必须写在上下文之外（进度文件、git）。
- Gas Town：把工作拆成很小的步骤，交给临时 worker 接力，相当于给 agent 用的调度器。代价很高。

### 1.7 共同规律

1. **瓶颈已经从写代码转到了验证和人的注意力上。** 最快的团队都在投资验证能力：一条命令、跑得快、能操作真实产品。
2. **规则要机械化。** 文字规则只是第三层。反复出现的问题会一路升级：lesson → 标准 → lint/hook/架构。
3. **人退出同步回路。** 可逆又已验证的改动由 agent 合并，人在合并后抽查、读每天的摘要。单向门（发布到不能回滚的渠道、数据、钱、安全）才停下来等人。
4. **往前修，接受小错误率**，前提是能快速回滚或更新。
5. **证据跟着提交走**（提交正文、PR 描述），不靠一套平行的任务文档。
6. **自主程度按信任阶梯逐级提高**，每升一级都要有数据。

## 2. 以后的方向（判断，不是事实）

- **近期（到 2027 年上半年）**：主流做法是"事件驱动的回路 + 小规模舰队"。一个人同时盯 5–20 个后台 agent，issue、告警、CI 失败自动起 agent 修，人每天看一次摘要。每个项目最值钱的资产是它的**验证 harness 和 lessons**，不是 prompt。
- **中期**：规划由 agent 递归完成，人只写目标和约束。审查基本变成多模型对抗加可执行证明，人工审查退到抽样和事后。按角色路由模型、控制成本会成为日常工作。
- **一直不变的**：方向、品味、单向门、对理解的负责（防止"认知投降"），这些仍然归人。

## 3. v1 对照

| 维度 | v1 现状 | 业界快速做法 | 判断 |
|---|---|---|---|
| 完成要有证据 | 有 | 有，并且要"亲手改坏" | 保留并加强 |
| 独立审查 | 每个标准档跨模型审一轮，P0–P3 | 对照 spec 审、只报 ≥P2、发现要能证明、倾向合并 | 门槛要调 |
| 诊断 RED/GREEN | 有 | 一致 | 保留 |
| 少打扰用户、三行汇报 | 有 | 一致 | 保留 |
| **合并授权** | 默认每次都问用户 | 可逆且已验证的由 agent 合并 | **最大的减速点** |
| **规则形态** | 全是 skill 里的文字（第三层） | hook、Stop hook、CI、lint | **缺机械层** |
| **验证能力** | "跑项目规定的命令" | 每个项目建自己的 verify CLI 和功能地图 | **缺最关键的投资** |
| 记录 | TASK 文件 + 看板 + 计划 + 决策记录 | 提交正文 + issue + LESSONS | 太重，共享文件容易冲突 |
| 沉淀 | 每个任务结束时被动写 | 每晚复盘合并流，按出现次数升级 | 缺频率和升级机制 |
| 并行 | 最多 2 个，总览是中心集成者 | 先有信任，再按阶梯扩容 | 上限要和信任挂钩 |
| 外循环 | 没有 | issue/反馈/告警 → 自动分派；定时清理 | 缺 |
| 档位依据 | 改动的类型和大小 | **可逆性 × 可验证性** | 换坐标轴 |

v1 的底线意识是对的，问题出在**把底线放在了人和流程上，而不是放在机器上**。

## 4. v2 架构

```
┌──────────── 人：方向 / 品味 / 单向门 / 每日摘要 ────────────┐
│                                                              │
│  外循环（routines）                                          │
│   intake: 用户对话 · issue · 反馈 · CI 失败 · 告警           │
│     → 队列（GitHub issues 或 docs/queue.md）                 │
│     → 编排者分派 N 个 owner（N 由信任等级决定）              │
│   每晚: 园丁复盘当天合并 → LESSONS（计数）→ 升级            │
│   每周: 清理熵（死代码、过时文档、技术债清单）               │
│                                                              │
│  内循环（每个改动，一个 owner agent，一个 worktree）         │
│   理解 → 做 → 在真实产物上证明 + 亲手改坏 → 独立验证方      │
│   → land（rebase、在推送的 head 上跑全量、合入主干、         │
│     提交正文写证据）→ 有问题往前修                           │
│                                                              │
│  项目 harness（项目里的东西，不在 skill 里）                 │
│   verify CLI · 功能地图 · AGENTS.md 目录 · 子系统文档        │
│   hooks（Stop 跑快检；PreToolUse 拦受保护路径和密钥）· CI    │
│   code-standards · LESSONS                                   │
└──────────────────────────────────────────────────────────────┘
```

### 4.1 档位：按可逆性 × 可验证性分

| 档 | 判定 | 谁合并 |
|---|---|---|
| **自走** | 可回滚（git revert 就能恢复，或客户端能自动更新），而且 verify 能覆盖 | agent 合并，进每日摘要 |
| **看一眼** | 可回滚，但正确性要靠人的品味（UI、文案、交互手感） | agent 做完，附截图或录屏，等人说"可以" |
| **单向门** | 发布到不能撤回的渠道、迁移或写入真实数据、钱、安全、对外发消息、删除 | 计划先确认，人授权才执行 |

"拿不准就按高一档"保留。

### 4.2 信任阶梯（每个项目各自记一个等级）

| 等级 | 自走档怎么合 | 并行上限 | 升级条件（建议） |
|---|---|---|---|
| L0 | 每次问人（相当于 v1） | 1–2 | 项目 harness 达到第 5 节的最低要求 |
| L1 | agent 摞好提交，人一次合一批（autopilot-stack） | 3 | 连续 2 周，批次里被人打回的 < 10% |
| L2 | agent 直接合进主干，人事后抽查 | 5 | 连续 2 周，合并后 48 小时内的返工率 < 15%，且没有单向门事故 |
| L3 | 外循环 routines 自动领单 | 按成本定 | 人决定 |

等级写在项目 `AGENTS.md` 里，由人来改，agent 只能**建议**升级或降级（附数据）。出一次单向门事故，自动退回 L1。

### 4.3 内循环细则

1. **理解**：先读 `AGENTS.md` 目录、相关子系统页、`LESSONS.md`，再读完整的 issue 或对话（magpie 吃过亏：报告人说"先别做"，agent 照做了然后被回滚）。
2. **做**：只做目标需要的部分，**修 bug 要修到所有同类位置**（grep 同样的写法）。
3. **证明**：
   - 在真实产物上验证：跑 verify CLI，需要时操作真实界面；不拿"能编译"当证据。
   - **亲手改坏**：把修复撤掉或把被测保证改坏，确认测试会红。
   - 跑全量，而不是挑几个包。主干上原来就红的测试也是 bug，要么当场修，要么开 issue 写明原因。
4. **独立验证方**：全新上下文、只读、模型不低于执行方。拿到 spec 和 diff，**不读执行方的自述**。审查说明里写死：
   - 对照目标和完成标准审；**skip style**；
   - 只报 P0–P2，每条要附可执行的证明（复现命令、失败的测试、具体输入）；拿不出证明的降为备注；
   - 结论对应的必须是要合并的那个 head，head 变了就重验。
   - 跨厂商审查（Codex/Claude 互审）是首选，但不再是每项必需：自走档可以用同厂商不低档的子 agent；单向门档必须跨厂商。
5. **land**：rebase 到主干，在**最终推送的 head**上跑全量，合并。提交正文按模板写（见 4.5）。合并后主干如果红了，立刻往前修或 revert，不等人。
6. 同一项连续 2 次验证不过，就丢掉 worktree、带着教训从头重来；再失败才找人。

### 4.4 外循环与园丁

- **队列**：优先用 GitHub issues（`gh` 可读可写，天然支持并发），没有远程就用 `docs/queue.md`，一行一项，只由编排者写。
- **编排者**只做分派、核对、合并排序，不写业务代码（这是 Cursor 的教训：角色要分开）。并行上限取信任等级对应的数字；会改同一批核心文件的任务串行。
- **每晚园丁**（routine 或 `/loop`）：
  1. 读上次复盘之后的全部合并（`LESSONS.md` 头部记 `reviewed-through: <sha>`）；
  2. 找三类问题：返工过的、不该合的、验证太薄的；
  3. 写进或更新 `LESSONS.md`：规则 → 原因 → 证据（提交 sha），并给"Seen N 天"加一；
  4. 被 3 个不同日子看到的，**升级**：能机械化的写成 lint、测试或 hook，不能的写进 `code-standards.md`，然后从 LESSONS 移走；
  5. 给人写一份每日摘要：合了什么、返工率、新增的教训、建议调整的信任等级。
- **每周清理**：删死代码，对照代码校正子系统文档，整理技术债清单。这类活交给便宜的模型。

### 4.5 记录：用提交正文替代 TASK 文件

默认不再建 TASK 文件。证据写在提交或 PR 的正文里：

```
<area>: <可观察的结果>（<报告人或 issue>）

为什么：<根因或动机，一两句>
跑了：<命令 → 结果；平台>
改坏验证：<撤掉什么 → 哪个测试红了>
没试：<诚实写>
审查：<验证方模型/强度 → 结论；没采纳的意见和理由>
```

TASK 文件只在两种情况下写：跨多天的计划，以及单向门档的方案确认。看板由队列（issues）代替。

### 4.6 项目 harness：v2 新增的 `harness` 模块负责搭建

agent 第一次进入一个项目，如果项目没有 harness，先把它搭起来，这一步本身就是一项任务：

1. **verify 入口**：一条命令（如 `scripts/verify` 或 `npm run verify`），包括格式化、类型检查、lint、单测；目标 2 分钟内跑完。另设 `verify:full`（全平台或 e2e）。
2. **能操作产品**：Web 项目用 Playwright 脚本加截图；桌面应用用一个 CLI，负责启动、驱动、抓日志和截图；CLI 项目用"样例输入 → 输出对比"。写一份**功能地图**（`docs/feature-map.md`）：每个功能从哪里进入、怎么验证。
3. **`AGENTS.md` 改成目录**：100 行以内，写验证命令、信任等级、单向门清单、各文档入口。
4. **hooks**（`.claude/settings.json`，Codex 那边用对应机制）：
   - Stop hook：跑快检，不过就不让结束这一轮；
   - PreToolUse：拦截写受保护路径（迁移、密钥、真实数据目录）；
   - 提交前扫描密钥。
   hook 只放**零例外**的规则，总数控制在个位数。
5. **CI**：主干上跑 `verify:full`，tag 只打在绿的提交上。
6. 空的 `LESSONS.md` 和 `code-standards.md`。

## 5. v2 的 skill 结构

```
skills/ai-dev-flow/
  SKILL.md             总览：档位（可逆性×可验证性）、信任等级、找人的时机、三行汇报
  modules/harness.md   新增：给项目搭 verify、功能地图、hooks、AGENTS 目录
  modules/build.md     替代 plan.md：内循环 1–3 步（理解/做/证明），只在跨多天时写计划
  modules/verify.md    替代 review.md：独立验证方说明模板、证明门槛、跨厂商规则、降级顺序
  modules/land.md      替代 ship.md：rebase、在推送的 head 上跑全量、提交正文模板、往前修和 revert
  modules/diagnose.md  保留，补"用报告人的原始字节做 fixture"和"修到所有同类位置"
  modules/orchestrate.md  改写：队列、编排者职责、信任等级对应的并行数、重开规则
  modules/garden.md    替代 compound.md：每晚复盘、Seen 计数、升级到 lint/标准、每日摘要、每周清理
```

### 保留 v1 的

- "没跑过不说通过"、"执行方不批准自己的工作"、RED/GREEN 诊断；
- 问题攒到一次问完，每个问题附推荐答案；三行汇报；
- 不碰真实数据，不提交密钥或本机路径；
- 审查方不降档。

### 删掉或降级的

- 标准档默认建 TASK，以及看板、六个状态词 → 改用提交正文加队列；
- 默认每次合并都问人 → 改由信任等级决定；
- 每个标准档必须跨模型审 → 只有单向门档必须；
- 最多 2 个并行的硬上限 → 跟信任等级挂钩。

---

## 6. 落地顺序（建议）

1. **先在一个真实项目上搭 harness**（verify、功能地图、Stop hook），观察一周。这一步收益最大，和 skill 怎么写无关。
2. 改 skill：先做 `SKILL.md`、`verify.md`、`land.md`、`garden.md`，项目从 L1 起步。
3. 用 `/schedule` 或 routine 跑每晚园丁，用两周的数据决定能不能升到 L2。
4. 最后再接外循环（issue 自动领单）。

## 7. 试点：用户的真实项目（2026-10-29 核对）

### 7.0 已定

- 用户愿意让 agent 自己合并（目标 L2）。
- 拿真实项目试，近期集中推 **02 天正引擎** 和 **01 导图项目**，CADCat 暂不动。
- 项目都还没发布、没有外部用户，所以"主干直推 + 有问题往前修"现在就安全，不需要先做自动更新。真正的单向门只有这几类：**客户图纸外传、操作用户正在用的 CAD、写真实图纸、花钱调用模型**。

### 7.1 两个项目共同的症状（v1 加上项目自己的 AGENTS.md 叠出来的）

| 症状 | 实例 |
|---|---|
| 记录比代码多，而且人读不懂 | 天正根目录有 30 多个 TASK 文件（最大 55KB），CURRENT.md 塞满 SHA 和内部代号；导图的 `项目方案.md` 有 209KB，README 状态段一段好几百字 |
| 证据仪式过重 | 每一步都要"冻结、SHA 绑定、有限独审、Passed 不等于业务通过"，大量 token 花在给审计写报告上 |
| 人在同步回路里 | 导图每次调模型都要"人类具体授权"，额度和预算按次批；agent 频繁"停在安全点等明确继续"，用户只能说"后续不要再动不动就停了" |
| 慢验证没法并行 | 天正的 CAD 宿主验证由 root 串行独占，还会被 COM 拒读、安全加载提示、截图失败卡住 |
| 收尾没清理 | 天正有 24 个 worktree 和对应分支没清；导图**根本没有 git 提交**（master 是空的） |
| 没有一个"北极星数字" | 进展用"N 项通过"描述，但每次的 N 口径都不一样，看不出离目标还有多远 |

### 7.2 天正引擎：把 CAD 宿主验证变成可并行的批处理

北极星：**兼容矩阵**，即"对象 × 格式（V8/基类5）× 宿主（2022+T20 / 2014+V2）"里，有多少格通过了"原生打开、改参、保存、重开"。

| 层 | 内容 | 目标耗时 |
|---|---|---|
| `verify`（快） | 构建，加上**全部已验收样例**重新生成，用 `compare-dwg-records` 做逐记录回归，再用 ACadSharp 独立读回 | 5 分钟内，不启动 CAD |
| `verify-host`（慢） | 候选 DWG 入队，宿主批量跑，结果写回矩阵 | 无人值守，可以夜里跑 |

关键实验（先做这一个）：本机有 `D:/Autodesk/AutoCAD 2022/accoreconsole.exe`。验证它能不能用脚本加载 T20 解释器和 HostProbe（HostProbe 现在引用了 `acmgd`，需要拆出只用 `accoremgd` 的版本），并且**同时起多个实例**。
- 能：宿主验证从串行、依赖 GUI 变成并行、无界面，最大的瓶颈就没了，也不会碰用户正在用的 CAD。
- 不能：保留单宿主，但改成队列加夜间批处理，白天只跑 `verify`。

**实验结果（2026-10-29，详见天正 `analysis/host-parallel-20261029/结果报告.md`）**：accoreconsole 走不通，因为 `tch_kernal.arx` 静态导入了 `ACAD.exe`，也没有 dbx 或 crx 版本。改走"完整 AutoCAD 后台多实例"：池大小 4 跑 12 个保存重开样例，总共 93.7 秒，全部 PASS，0 代理，平均每个约 7.8 秒（串行 37.9 秒），约 5 倍提速。8 个并行没有更快，还出现了 1 次退出时崩溃。所以 `verify-host` 用 4 个工位的队列。补测：COM 改参类 12 个、7.3MB 大图 8 个，并行结果都和串行逐字段一致（大图约 2 倍提速）。大图全量枚举在串行下就超过 15 分钟，需要另给探针加快速模式。

其他：
- 根目录的 TASK 文件归档到 `docs/tasks/`；CURRENT.md 改成一页以内的白话，内容是矩阵现状、正在做什么、卡在哪；SHA 只留在提交正文和 evidence 里。
- 清理已合并的 worktree 和分支（要用户授权）。
- 每晚园丁：把当天被打回或返工的问题写进 LESSONS，并更新矩阵。

### 7.3 导图项目：以测试集分数为核心的爬山回路

北极星：**`03 AI识别测试集` v1.0 的评分**（23 张纸、41 个视图），再加上"能出可交付 DWG 的视图数"。

1. **先 `git init` 并做首次提交**（AGENTS.md 本来就要求问，这次一起授权）。`实测/` 下的大文件用 `.gitignore` 排除，或者只提交报告。
2. `eval` 一条命令：在固定的子集（比如 5 张纸）上跑"识别 → 检查 → 生成 → 评分"，输出一张分数表加费用。全量 23 张只在晚上或有大改动时跑。
3. **用预算代替逐次授权**：用户定一个额度（比如每天多少元、每轮最多几次模型调用），额度内 agent 自己调模型做实验，只在超额时停。测试集是自制和已脱敏的样本，不涉及客户图外传；**客户原图仍然是单向门**。
4. 回路形状照搬 pstack 的 hillclimb：每次只改一个变量（提示词、裁图、纠错策略、工具），跑 `eval`，**分数涨了就提交，没涨就丢掉**。每次都记一行"改了什么 → 分数 → 费用"。
5. `项目方案.md` 拆开：方案正文单独留着，进度改成一张分数曲线表加最近 5 条，旧进度归档。

### 7.4 起步顺序

| 步 | 做什么 | 需要用户 |
|---|---|---|
| 1 | v2 skill 先写出 `SKILL.md`、`harness.md`、`verify.md`、`land.md`、`garden.md` | 无 |
| 2 | 导图：git init、首次提交、`eval` 命令、预算规则写进 AGENTS.md | 授权 git init，定预算 |
| 3 | 天正：accoreconsole 并行可行性实验（用副本，不碰用户的 CAD） | 授权跑无界面宿主 |
| 4 | 天正：`verify` 快速回归，文档瘦身，清理 worktree | 授权删已合并的分支和 worktree |
| 5 | 两个项目开每晚园丁，从 L1 起步，两周后看数据决定是否升 L2 | 无 |

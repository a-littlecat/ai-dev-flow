# 独立验证

执行方说"好了"不算数。合并前要有另一个验证方给出结论，而且结论对应的必须是要合并的那个版本。在主上下文里切换角色自己复查，不算独立验证。

## 1. 什么时候验、谁来验

| 档 | 验证 |
|---|---|
| 自走 | 一轮。写和审不是同一个会话，审的模型不低于写的；同厂商的子 agent 可以 |
| 看一眼 | 一轮，另加用户看 |
| 单向门 | 跨厂商（Claude 和 Codex 互审），一直验到没有 P0 / P1 |
| 只改纯文档（不改代码、脚本、hook、CI 和配置） | 不跑全量快检，不必请验证方：把文档里写的路径、命令、章节引用逐条实际查一遍或跑一遍，项目有文档格式检查的跑它。这是总览第 5 节"合并前要有独立结论"唯一的例外 |

改验证脚本、hook、CI 配置的，等于改了门禁本身，一定要独立验证：验证方要亲手改坏一处被测代码，从门禁的入口命令确认改过的门禁真的会红（第 3 节）。

项目另有规定的，按项目执行。

## 2. 独立性从哪里来

- **全新上下文**，模型不低于执行方。**不改候选版本**：不改候选分支，不提交，不改执行方的 worktree。验证方在为它单独开的临时 worktree 里工作，可以在那里写构建产物（`bin/`、`obj/`、缓存），也可以为改坏检查临时改源码，改完恢复。
- **只给目标、完成标准和 diff**，不给执行方的自述、总结或 PR 描述，让它自己判断。
- **开了合并后全量的项目**（`build.md` 第 3 节），验证方合并前只跑对照表按 diff 选出的测试，不跑全量；对照表选不出来的改动照下一条跑全量。只跑了相关测试的，note 里"没跑："写"无"，另起一句"全量：合并后由 trunk-check 跑"；"快检用时"只写全量的用时，只跑了相关测试的不写（状态页拿它判断快检慢不慢，`land.md` 第 2 节）。
- **门禁看账，不看自述**：验证方在临时 worktree 里经 `verify-ledger.ps1 -Command '<快检命令>'` 跑快检（`build.md` 第 3 节），不信执行方贴出来的结果，输出里写明命令、退出码和 head。账上这棵树已经跑绿过的（脚本跑出来记的，不是谁贴的），它打出那条记录就结束，验证方不再重跑全量，把那条记录写进输出，时间花在读代码、写针对性的复现和改坏检查上；没绿过的，就在候选 head 上跑这一次完整快检；快检要传基准的，用说明里的 base，不按几个基准各跑一遍。这一次就是这个 head 的门禁结果，总览核对和合并后都不再重跑（`land.md` 第 2 节）。项目启用了执行方不跑全量（`build.md` 第 3 节）的，这也是这个 head 唯一的一次全量快检，没有别的结果兜底；跑不全的按 `land.md` 第 2 节由总览补跑，不能算通过。慢验证不重跑，读队列留下的结果文件，核对它对应的是同一个 head。
- **专门找问题**，不必肯定已有做法；但要倾向通过：没有带证明的严重问题，就给通过。

## 3. 验证说明模板

把说明写成一个自包含的临时文件：

```
目标与完成标准：<来自对话、issue 或计划>
基准：临时 worktree <tmp>（检出 head），分支 <branch>，base <sha>，head <sha>（要合并的那个版本）
项目规则：AGENTS.md、docs/code-standards.md、LESSONS.md
慢验证结果：<结果文件路径，及其对应的 head；没有就写"无">
要求：
- 只在 <tmp> 里工作：不提交，不碰候选分支和其他目录。构建产物可以留在 <tmp> 里。
- 要对照主干或旧版本、自己另开 worktree 的，交回结论之前用 git worktree remove --force 删掉，输出里写删了哪个；<tmp> 留给派你的会话核对和删。
- 在 <tmp> 里跑一次 pwsh -NoProfile -File <skill>/scripts/verify-ledger.ps1 -Command '<verify 命令>'（要传基准的用上面的 base，只跑这一次；这棵树账上已绿的，它打出记录就结束，不再重跑，照它打出的写），把命令、退出码、head 和用时（`快检用时：<秒> 秒`，只写全量的；开了合并后全量、只跑了对照表选出的测试的，不写这一句，另写"全量：合并后由 trunk-check 跑"）写进输出；因环境原因跑不全的（沙箱拦了某些测试等），单列一行"没跑：<哪些检查>（<原因>）"，全跑了写"没跑：无"，只改文档的写"没跑：不适用"。
- 改坏检查（改了验证脚本、hook、CI 时必做）：在 <tmp> 里临时改坏一处被测代码，从门禁的入口命令确认变红
  （可以只跑入口里覆盖这一处的那一段，不必跑完整快检），记下改了什么、哪个检查红了；
  然后把自己改的地方改回原样（不用 git checkout，沙箱里可能写不了 Git 索引），
  用 git -C <tmp> diff --stat 确认没有差异。没有差异就是刚才跑过完整快检的那份代码，不再重跑。
- 结果是新写的评分、读回、比较工具判出来的：核对它拿已知对、已知错各跑过一例（`build.md` 第 3 节），判定脚本和证据都在提交里。缺了，这次判定不算证据。
- 对照目标和完成标准审。skip style：命名、格式、写法偏好都不报。
- 改了功能的（只改文档的按第 1 节，不看这一条），看提交正文有没有对真实数据只读跑一次的命令和结果（`build.md` 第 3 节）：没有、也没写"真实数据：没有，<原因>"的报 P1；自己能拿到同样的真实数据的，照它写的只读跑一次，结果对不上的按问题报。新加的测试超出最关键的一两条、又和已有测试查的是同一件事的，写进备注，不算问题。
- 看 diff 里有没有没报决定卡就做了的方向性选择（`direction.md` 第 3 节）：有的报 P1，证明写清是哪个选择、队列或 `docs/decisions/` 里没有用户的决定。改了步骤或模型和程序的分工、流程图（`docs/flow.html` 或 `docs/flow.md`）却没在同一改动里更新的，也报 P1（`direction.md` 第 6 节）。
- 交回的结果说明做法本身不成立的（例如工具实测准确率远低于目标、抽查的问题多半是误报，修补也到不了完成标准），结论之前单独写一行"前提不成立：<实测数字和依据>"，不要只当成一条 P1。
- 只报 P0–P2。每条附可执行的证明：复现命令、会失败的测试、具体输入和错误输出。
  拿不出证明的写进"备注"，不算问题。
- 没有带证明的 P0 / P1，就给 Pass。
输出：
- 每条：ID ｜ P0–P2 ｜ 文件:行 ｜ 问题 ｜ 证明 ｜ 建议修法
- 结论：Pass 或 Fix
- 没覆盖到的风险
```

严重度：P0 阻止合并；P1 合并前必须修；P2 可以以后修。P2 只把实际使用中会碰到的（说得出谁、在什么情况下碰到）排进队列，来源写"审查 #n"，没挂本周目标、也不挡当前项的写"待放行"（`skills/next/SKILL.md` 第 4 节）；只有构造出来的输入才会触发的，写进验证记录的"没采纳"，不排。

## 4. 发起

验证放在后台跑，等待期间继续做别的事。

先在主项目工作区（不要在别的 worktree 里，否则会嵌套）为验证方开一个临时 worktree，检出要合并的 head（用 `scripts/dispatch.ps1 -Review` 派给外部 agent 时，脚本会自动开好）：

```bash
git worktree add --detach .agents/worktrees/<运行名> <head>
```

只改了文档的 diff（改名算删＋增，子模块和链接不算），验证方不跑快检，改成把文档里的路径、命令、源码位置逐条实际查一遍或跑一遍。

用 `dispatch.ps1 -Review` 派的，脚本在审完时自己删临时 worktree：未跟踪文件先复制到 `.agents/runs/<运行名>/worktree-files/`，改动过被跟踪文件的留着不删，`exit.json` 的 `ReviewWorktree` 写着结果。写 `kept: tracked files changed` 的，改坏检查没恢复，这轮结论作废重来；其他的 `kept`（超大、被占用）不影响结论，之后用 `-CleanReviews` 清。下面的删除步骤只适用于你自己开的。

验证结束后核对两件事：候选分支的 head 没变；`git -C <tmp> status --short` 里没有改动被跟踪的文件（未跟踪的构建产物不算；改坏检查没恢复的，这轮结论作废重来）。然后用 `git worktree remove --force <tmp>` 删掉这个临时 worktree。它是你为验证自己建的，删它不需要用户授权。验证方（常见是子 agent）为对照主干或旧版本自己另开的 worktree，由它在交回结论之前删掉，结论里写一句删了哪个（第 3 节模板）；派它的会话收到结论后用 `git worktree list` 看一眼，没删的当场删。候选后来改写了的，这类 worktree 停在不在主干里的分离头上，合并后谁也不会再碰它，`cleanup.ps1` 只列出、不删。

所有验证方式都在 `<tmp>` 里跑，都要能写 `<tmp>`，不要用会挡住构建的只读模式。

**Claude 执行的项**

- 自走、看一眼档：用 Agent 工具开全新上下文的子 agent，说明照第 3 节写。推理强度用 `high`。
- 单向门档：请 Codex。PowerShell 中：

```powershell
Get-Content -Raw -Encoding UTF8 <brief.md> | codex exec --ephemeral --sandbox workspace-write -m <model> -c model_reasoning_effort=high -C <tmp> -o <out.md> -
```

Bash 中不用 `Get-Content` 管道，直接从文件读入：

```bash
codex exec --ephemeral --sandbox workspace-write -m <model> -c model_reasoning_effort=high -C <tmp> -o <out.md> - < <brief.md>
```

`workspace-write` 把写权限限制在 `<tmp>` 里；其余要求写在说明里，结束后按上面的方法核对。

**Codex 执行的项**：自走、看一眼档用 Codex 原生的子 agent，工作目录设为 `<tmp>`；单向门档请 Claude（在 `<tmp>` 里运行 `claude -p`，只允许它写 `<tmp>`）。

**项目配了 `scripts/dispatch.json` 的**：用 `scripts/dispatch.ps1 -Review <分支> -Agent <agent>` 派，Codex、Claude 哪个配了、哪边有额度用哪个（`orchestrate.md` 第 3 节）。规则同上：写和审不是同一个会话，审的模型不低于写的（`-Model` 指定）；单向门档选另一家厂商的 agent。

### 首选验证方不可用时

报额度、限流、未登录或超时，按下面的顺序换，不要因此跳过验证：

1. 限流这类可能很快恢复的：过一会儿用同一模型、同一推理强度重试一次。明确报额度用完的，直接跳到下一步。
2. 换成另一种同厂商的方式（Agent 子 agent 或原生子 agent），**模型不得低于执行方**，推理强度单向门档用 `xhigh` 或 `max`。不要为了"换个模型"而降档，那会削弱验证。
3. 单向门档原本要求跨厂商的，告诉用户首选验证方不可用，由用户决定是等它恢复还是接受同厂商的结论。

如实记录：验证记录（第 6 节）里写明验证方是谁（模型、推理强度），以及为什么没用首选。

## 5. 处理结论

这一步由你判断，不要转给用户：

- 每条意见先对照代码和目标核实，确认是真问题再改。没采纳的，在验证记录里写一句理由。
- head 一变，结论就作废，包括修意见、重新 rebase、squash。复验时把这次的变化发给验证方：修了意见的，发修改部分和上一轮每条的处理结果；因为主干前进而重新 rebase 的，发 rebase 带进来的主干改动，让验证方看两者合在一起是否还成立。新结论要对应新的 head。
- 例外：原结论是 Pass、没有未处理的 P0 / P1，而新 head 和验证过的 head 之间只多了纯文档改动（`git diff --name-only <验证过的 head> <新 head>` 列出的都是文档，判定同第 1 节），结论沿用，不重审；那个 head 上的快检和慢验证结果也一并算数。多出的文档里不是从主干带进来的，按第 1 节逐条核对。然后在新 head 上按第 6 节补一条 note，覆盖范围写新的：
  ```bash
  git notes --ref=verify add -f -m "覆盖：<新 base>..<新 head>；沿用 <验证过的 head> 的 Pass（<验证方模型和推理强度>）；之后只多了文档：<文件>，<逐条核对的结果，全是主干带进来的写不涉及>；没跑：<同原 note，原 note 的补跑也照抄>；没采纳：<同原 note>" <新 head>
  ```
  多出的有代码、脚本、hook、CI 或配置的，照常复验。
- 结论里有"前提不成立"的，先核实数字；成立的，这一项不派回去修，按总览第 3 节第 5 条停下报用户。
- 验证方和执行方意见不一致时，以能跑出来的证明为准。

## 6. 验证记录

结论不写进提交正文，因为改正文会改变 head、让结论作废。用 git note 挂在被验证的那个提交上，它不改变 head，快进合并后仍然跟着这个提交：

```bash
git notes --ref=verify add -f -m "覆盖：<base>..<head>；<验证方模型和推理强度> → Pass；跑了：<命令 → 结果>；快检用时：<秒> 秒；没跑：<检查（原因），全跑了写无>；没采纳：<意见和理由，没有写无>" <head>
```

"没跑："不是"无"的，合并前按 `land.md` 第 2 节在这个 head 上补跑，结果追加到同一条 note，`land-check.ps1` 认这一句：

```bash
git notes --ref=verify append -m "补跑：<命令> → 退出 0（<head>）" <head>
```

`<base>` 写这一项在主干上的起点（`git merge-base <主干> <head>`）；叠在另一个候选分支上的，写那个候选的 head。复验即使只发了这一轮的修改部分，`覆盖：` 也写整段，不写上一轮被打回的 head：`land-check.ps1` 顺着起点往下找，起点不在主干里的要有它自己的 Pass note（`land.md` 第 2 节）。

验证方输出的完整文件放在项目的证据目录（仓库外，`build.md` 第 3 节）或临时目录里，note 里给路径；只放在审查 worktree 里的，合并后会被 `-CleanReviews` 删掉（`land.md` 第 6 节），要长期留的结论写进 note。项目用 PR 合并的，同样的内容写进 PR 描述。

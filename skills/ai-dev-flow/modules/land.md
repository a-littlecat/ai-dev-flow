# 合并落地

## 1. 谁来合

| 档 | L0 | L1 | L2 及以上 |
|---|---|---|---|
| 自走 | 问用户 | 摞好，用户一次合一批（第 5 节） | 你直接合 |
| 看一眼 | 用户说"可以"后你合 | 同左 | 同左 |
| 单向门 | 用户授权后执行 | 同左 | 同左 |

用户说过"验收通过""可以合并"的，直接合，不再问。合并到本地主干能撤回；push、打 tag、发布是单向门，除非项目 `AGENTS.md` 写明授权（例如"可以 push 到自己的私有远程"）。

## 2. 合并前

任何一项不满足，就回到 `build.md` 或 `verify.md`，不要硬合：

- 独立验证结论是 Pass，对应当前 head，没有未处理的 P0 / P1。
- 已 rebase 到最新主干。rebase 时解决过冲突，或者代码有了 rebase 以外的变化：重新验证。干净的 rebase：在新 head 上重跑 verify 即可。
- 主项目工作区干净：`git status --short`。
- `git diff --check <主干>..<分支>` 通过，diff 里只有本项的文件。
- 冲突：共享文档的冲突你来合；业务代码的冲突回到 worktree 里解决并重新验证；解决不了就找用户。

## 3. 合并

把分支整理成一个提交（或少数几个各自有意义的提交），证据写进提交正文，然后快进：

```bash
git merge --ff-only <分支>
```

项目规定用 `--no-ff` 或 PR 合并的，按项目执行；证据写进合并提交或 PR 描述。

## 4. 提交正文模板

```
<区域>: <可观察的结果>（<报告人或 issue>）

为什么：<根因或动机，一两句>
跑了：<命令 → 结果；平台>
改坏验证：<撤掉了什么 → 哪个测试红了>
没试：<诚实写；没有就写"无">
验证：<验证方模型和推理强度 → 结论；没采纳的意见和理由>
修复：<如果这是往前修，写被修的那个提交的 sha；否则删掉这一行>
```

"修复"一行是复盘统计返工率的依据，往前修时一定要写。

## 5. L1：摞好等用户

- 每一项在自己的分支上验证通过，并按依赖排好顺序。
- 汇报时一行一项：结果、验证结论、要不要看什么。用户回"都合"或者挑几项。
- 被用户打回的，记在队列对应那一项上，复盘时统计打回率。

## 6. 合并后

- 在主干上跑 verify。红了就立刻处理，不等人：原因清楚、改动小的，往前修；原因不清或改动大的，`git revert`。然后在汇报里说明。
- 关掉队列里对应的那一项。
- 提醒其他进行中的 worktree 同步主干。
- 已合并的 worktree 和分支：项目 `AGENTS.md` 授权了清理的就清；没有授权的，在汇报的"要你做"里列一行，等用户发话。push、打 tag、发布同样列在这一行。

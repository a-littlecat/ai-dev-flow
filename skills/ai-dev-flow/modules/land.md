# 合并落地

## 1. 谁来合

| 档 | L0 | L1 | L2 及以上 |
|---|---|---|---|
| 自走 | 问用户 | 摞好，用户一次合一批（第 5 节） | 你直接合 |
| 看一眼 | 用户说"可以"后你合 | 同左 | 同左 |
| 单向门 | 用户授权后执行 | 同左 | 同左 |

用户说过"验收通过""可以合并"的，直接合，不再问。合并到本地主干能撤回；push、打 tag、发布是单向门，除非项目 `AGENTS.md` 写明授权（例如"可以 push 到自己的私有远程"）。

## 2. 合并前

任何一项不满足，就回到 `build.md` 或 `verify.md`，不要硬合。能机械判断的几项（检出主干、工作区干净、能快进、`diff --check`、head 上有覆盖它的 Pass note、note 里"没跑："的检查已经补跑）由脚本查，在主项目工作区运行：

```powershell
pwsh -NoProfile -File <skill>/scripts/land-check.ps1 -Branch <分支> [-Trunk <主干>]
```

退出码非 0 就不合，按它列的原因回去改。叠在另一个候选分支上的，脚本顺着 note 的覆盖范围往下查，每一层都要有 Pass note。退出 0 只说明这几项满足，下面要人判断的几条（快检是否跑全、慢验证、diff 里只有本项的文件）仍要你核对：


- 分支已按 `build.md` 第 4 节定稿：rebase 到主干、整理好提交、写好提交正文。
- 独立验证结论是 Pass，对应的就是现在的 head，没有未处理的 P0 / P1：`git notes --ref=verify show <head>` 能看到这条记录（`verify.md` 第 6 节），或者按 `verify.md` 第 5 节的例外补的沿用记录。只改纯文档的，按 `verify.md` 第 1 节的例外，逐条核对过文档即可。
- 快检在最终版本上通过过。**同一份代码只跑一次**：验证方在某个 head 上完整跑过快检并通过，这次就算数，你核对时和合并后都不再重跑。只有两种情况你要在最终 head 上补跑一次：验证方因环境原因没跑全（note 里"没跑："不是"无"，补跑结果按 `verify.md` 第 6 节追加到 note，合并之前做，不留到合并之后）；最终 head 和验证方的 head 之间有非纯文档的差别（例如合进主干后带进了别的代码），用 `git diff --name-only <验证方 head> <最终 head>` 看。
- 按影响面选出的慢验证，在这个 head 上已经通过；结果对应的 head 和这个 head 之间只差纯文档的，同样算数。结果还没回来的，保持待合并，先做别的。
- 分支的 head 是主干的直接后代，可以快进。主干在验证期间前进了的，回到 `build.md` 第 4 节重新定稿、按 `verify.md` 第 5 节复验，不拿旧结论合并；rebase 后只多了纯文档改动的，按那里的例外沿用结论。
- 主项目工作区干净：`git status --short`。
- `git diff --check <主干>..<分支>` 通过，diff 里只有本项的文件。

## 3. 合并

合并时不再改提交，`land-check.ps1` 退出 0 后直接快进（它最后一行打的就是这条命令）：

```bash
git merge --ff-only <分支>
```

项目规定用 `--no-ff` 或 PR 合并的，按项目执行；证据写进合并提交或 PR 描述。

## 4. 提交正文模板

```
<区域>: <可观察的结果>（<报告人或 issue>）

为什么：<根因或动机，一两句>
跑了：<命令 → 结果；平台>
改坏验证：<撤掉了什么 → 哪个测试红了>
没试：<诚实写；没有就写"无">
修复：<如果这是往前修，写被修的那个提交的 sha；否则删掉这一行>
```

"修复"一行是复盘统计返工率的依据，往前修时一定要写。验证结论不写在这里，写在 git note 里（`verify.md` 第 6 节）。

## 5. L1：摞好等用户

- 每一项在自己的分支上验证通过，并按依赖排好顺序。
- 汇报时一行一项：结果、验证结论、要不要看什么。用户回"都合"或者挑几项。
- 被用户打回的，记在队列对应那一项上，复盘时统计打回率。

## 6. 合并后

- 主干的内容和通过快检的那个 head 相同（快进合并就是这样，`git rev-parse <主干>^{tree} <head>^{tree}` 两行一样），或者只多了纯文档改动，不再跑；否则在主干上跑一次 verify。红了就立刻处理，不等人：原因清楚、改动小的，往前修；原因不清或改动大的，`git revert`。然后在汇报里说明。
- 关掉队列里对应的那一项。
- 提醒其他进行中的 worktree 同步主干。
- 已合并的 worktree 和分支当场删，不用问（用户 2026-11-03 定，所有项目默认如此；项目 `AGENTS.md` 写明"不自动清理"的除外）。不手工删，在主项目工作区运行脚本（`land-check.ps1` 通过时也会打出这一行）：
  ```powershell
  pwsh -NoProfile -File <skill>/scripts/cleanup.ps1 -Branch <刚合并的分支> [-Trunk <主干>]
  ```
  worktree 只删同时满足的：分支或分离头的 head 已经是主干的祖先；`git status --short` 没有输出；被忽略的文件都是构建产物（证据、`.env` 这类留着）；里面没嵌别的 worktree；没上锁；没有派活在跑，也没有会话在里面。没点名的 worktree 另外要 60 分钟内没有动静（刚开出来的 worktree，head 也在主干上，可能正有会话在用）。分支只删已合进主干的，主干和 `release`、`develop`、`backup` 这类长期分支不删。用 `git worktree remove` 和 `git branch -d`，不加 `--force`、不用 `-D`，Git 拒绝的留着，脚本列出原因，在汇报里说明。退出 1 表示有目录卡在 `.cleanup-probe` 名下，输出里写着要怎么改回：停下来报给用户，改回之前脚本不清任何记录。没合并的、有未提交改动或未跟踪文件的，一律不动；其中停在分离头、提交不在主干里的（多半是审查用过、候选后来改写了的临时 worktree），脚本列在"留着"里：过了上面同样的检查的附上删除命令，确认不要了就删；命中哪一项（有改动、被忽略的证据、上锁、有派活或会话在用）就只写原因，先看一眼。审查用的临时 worktree 留着未跟踪证据的不走这一条：`dispatch.ps1 -Review` 审完自己删，证据复制到运行记录里。合并后在项目仓库里运行 `pwsh -NoProfile -File <skill>/scripts/dispatch.ps1 -CleanReviews`（直接调 skill 里的脚本，项目入口脚本不一定转发这个开关）：审查的版本已经合进基准分支的，证据和旧 worktree 直接删，不用问（用户 2026-11-05 定），只留 `final.md`、`exit.json` 等运行记录；没合并的先复制证据再删 worktree；改动过被跟踪文件的不动。证据删掉后找不回来，要查只能重跑。
- push、打 tag、发布，项目 `AGENTS.md` 没授权的，在汇报的"要你做"里列一行，等用户发话。

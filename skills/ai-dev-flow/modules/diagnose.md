# 诊断

适用于 bug、性能变慢、原因不明的测试失败、实机报错、用户验收没通过。

先要有能区分对错的信号，再改代码。凭猜测修改，往往会再造出一个 bug。

## 1. 验收没通过：先分类

用户说"不对""不符合预期"时，先只读分类，再决定动不动代码：

- 原来那项没做完，或者引入了回归 → 在原来那项里修；已经合并的，往前修，提交正文写"修复：<sha>"
- 新需求或范围扩大 → 进队列作为新的一项，在汇报里说明，不塞进旧的那项
- 环境或配置问题 → 记录下来，修环境
- 证据不够 → 按第 3 节补最小证据

## 2. 定义信号

- **RED**：现在能观察到的失败，例如报错文本、错误输出、文件差异、耗时超过多少。
- **GREEN**：修好以后应该看到什么。
- **SIGNAL**：从哪里取证，例如命令、测试、日志、截图、输出文件。

## 3. 建复现回路

按成本从低到高，选第一个可行的：

1. 现有测试，或新写一个会失败的测试
2. 命令行加样例输入，对比输出。**能拿到报告人的原始文件或原始输入，就用它（的副本）做 fixture**，不要自己另造一个"差不多"的
3. 回放抓到的真实输入或日志
4. 写一个最小 harness，只跑出问题的那一段
5. 用两个版本或两套配置跑同一输入做对比；能二分就用 `git bisect run`
6. 必须由用户操作时（总览第 3 节第 2 种情况），给出最短步骤：准备什么、做哪几步、看到什么算失败或通过、回传什么

回路越快、越稳定越好。偶发问题先测出复现率。

## 4. 假设与验证

- 每个假设都写成预测的形式："如果原因是 X，那么改 Y 问题会消失，改 Z 会更糟"。说不出预测的假设，直接丢掉。
- 一次只改一个变量。临时日志加唯一前缀（如 `[DIAG-<主题>]`），收尾时 grep 一次清掉。
- 性能问题先测基线再改，不要靠日志去猜。
- 暂时复现不了：继续只读排查代码和日志，同时记下还缺什么证据。不要凭没有证据的假设去改生产行为。

## 5. 修复与回归

- 用同一个信号证明 RED 消失、GREEN 成立。
- **修到所有同类位置**：找到根因后，grep 同样的写法和调用，一起修掉，不要只修报告的那一处。
- 有合适的测试缝隙就留下回归测试，并亲手撤掉修复确认它会红；没有缝隙就写明缺口，不为了能写测试去强行重构。
- 同一根因连续 3 次修改，信号都没有变好：按 `build.md` 第 5 节从头重来；重来后仍然不行，就找用户，说清证据和可选的下一步。
- 发现超出本项的架构问题：进队列作为后续建议，不在修 bug 时顺手重构。

## 6. 收尾

- [ ] 原来的失败场景已验证消失
- [ ] 同类位置已经查过
- [ ] 临时诊断日志已清理
- [ ] 提交正文写明根因、修复、改坏验证和剩余缺口
- [ ] 值得以后查的疑难问题，写进 `docs/solutions/<主题>.md`（现象 → 根因 → 解法 → 怎么验证）

# 做：理解 → 做 → 证明

每个改动由一个执行方在自己的 worktree 里完成，做完交给独立验证（`verify.md`），再合并（`land.md`）。

## 1. 理解

- 先读 `AGENTS.md` 目录、`docs/feature-map.md` 和相关子系统文档、`LESSONS.md`、`docs/code-standards.md`。
- 读完整的来源：整段对话、issue 的全部评论。用户或报告人说过"先别做""等一下"的，照办。
- 能查清的不问。会改变范围或后果的问题，按总览第 3 节问；其他模糊点写成默认假设往下做，在提交正文里写一句，用户之后可以推翻。

要开新方向，或者碰到方向性选择（换路线、加砍子系统、改评分口径或北极星、改上线范围、超预算）：先照 `direction.md`，不直接开工。

### 什么时候写计划

只有两种情况写 `docs/plans/<主题>.md`：

- 要跨几天、拆成多项；
- 单向门档：方案先给用户确认。

计划只写：目标与非目标、方案和主要取舍、拆成哪几项和先后依赖、每一项怎么证明、要用户拍板的点。拆出的各项进队列。其他情况直接做——最好的说明就是代码。

## 2. 做

- 一个改动一个 worktree 和分支。只改文档的可以直接在主干上做。
- 只做目标需要的部分。不留 TODO，不交半成品。
- **修 bug 要修到所有同类位置**：grep 同样的写法、同样的调用，一起改掉。
- 契约变了（接口、文件格式、子系统行为），在同一个改动里更新对应的文档和功能地图。
- 同一句提醒要写第二遍时，改成代码：测试、lint、类型、断言。

## 3. 证明

- **在真实产物上验证**：跑 verify；用户能看到的行为，按功能地图里的方式实际操作一遍。"能编译"不是证据。
- **亲手改坏**：把修复撤掉，或把被测的保证改坏，跑覆盖这一处的测试，确认会红，再恢复，用 `git diff --stat` 确认和改坏前一样。不为改坏再跑一遍全量快检。改的是验证脚本、hook、CI 这些门禁本身的，要从门禁的入口命令确认它会红（可以只跑入口里相关的那一段），不能只单独跑测试文件。做不到的，在提交正文里写明原因。
- **跑全量快检**，在第 4 节定稿的 head 上跑一次，不要只挑几个包。主干上原来就红的测试也是问题：能当场修就修，修不了就进队列，写明原因。
- **例外：执行方不跑全量**。快检超过 10 分钟，或本机内存紧张要降并行才跑得动的项目，可以在 `AGENTS.md` 里写明启用（用 `dispatch.ps1` 派活的，同时在配置里写 `"builderVerify": "related"`）。启用后执行方只跑构建、和改动相关的测试、改坏验证，把跑了什么写进提交正文；全量快检交给验证方在候选 head 上跑一次（`verify.md` 第 2 节）。代价是全量才发现的问题要等到验证方才打回，多一轮执行和审查。默认不启用：快检只要几分钟，执行方自己跑一次比被打回一轮便宜；启用后打回多到抵消省下的时间，就改回来。
- **判定工具先自验**：用新写的评分、读回、比较工具判结果之前，先拿已知真值跑一遍，已知对、已知错各一例，看它判得对不对，结果写进证据。判定用的脚本、真值样本和一页结论入库，事后才能复核那次判定。工具自己有错，会把好坏判反。
- **慢验证按影响面选**：按功能地图，改动碰到了哪个区域，就把对应的慢验证排进项目的慢验证队列；没碰到的不跑，留给复盘时的全量。整图、全量枚举这类最慢的检查不进日常流程。
- **看一眼档**：附截图、录屏或样例输出，写清看哪里、看到什么算对。
- **原始输出不进仓库**：导出的 json、日志、图纸和数据副本、编译产物、反编译源码这类原始输出，放仓库外的证据目录（默认 `.agents/evidence/<项编号>/`，已被 `.gitignore` 忽略），提交正文写路径和摘要。一项的提交里新增文件超过几 MB，先看是不是原始输出。原始输出入了库，每开一个 worktree 都要检出它们，`git status` 和 rebase 也要扫它们，会越来越慢（一个项目这样攒到了 11 万个文件、2.6 GB）。
- 记下命令、结果和平台，合并时写进提交正文。

## 4. 定稿，交给独立验证

验证结论只对一个确定的版本有效，所以先定稿再验证：

1. rebase 到最新主干，解决冲突。
2. 把分支整理成最终要合并的提交（一个，或少数几个各自有意义的），写好提交正文（模板见 `land.md`）。
3. 在这个 head 上重跑快检（项目启用了第 3 节的例外的，改成只跑构建和相关测试）和按影响面选出的慢验证。验证过以后重新定稿（rebase 或修意见），新 head 只多了纯文档改动的，不重跑，按 `verify.md` 第 5 节的例外沿用。
4. 按 `verify.md` 发起独立验证，说明里写明这个 head。

定稿以后不再改提交；需要改，就回到第 1 步。验证方的结论回来之前，可以先做不依赖它的下一项。

## 5. 从头重来

- 同一项的独立验证连续 2 次不通过：丢掉这个 worktree，带着"试过什么、为什么不行"从最新主干重新开始。不要在一堆补丁上继续叠补丁。
- 重来以后仍然通不过，按总览第 3 节第 4 种情况找用户，说清证据和可选的下一步。

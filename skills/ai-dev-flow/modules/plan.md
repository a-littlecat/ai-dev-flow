# 计划与建任务

适用于需求不清、需要写计划、或者标准 / 高风险档要建 TASK 的时候。

## 1. 先查再问

- 先读代码、项目文档和已有 TASK，能查清的不问。
- 只有会改变范围、验收标准或风险决策的问题，才交给用户决定，按总览第 2 节的方式一次问完。
- 其他模糊点写成"默认假设"直接往下做，用户之后可以推翻。

## 2. 要不要先写计划

- 涉及多个模块、要跨几个会话、或者有几条方向要选：先在项目的计划目录（如 `docs/plans/`）写计划。高风险档要先请用户确认方向。
- 其他情况直接建 TASK。

计划只写这些：

- 目标与非目标
- 方案和主要取舍
- 拆成哪些任务，先后依赖是什么
- 每个任务怎么验收
- 需要用户拍板的点

## 3. TASK 模板

```markdown
# <ID>：<标题>

状态：Ready ｜ 档位：标准 / 高风险 ｜ base：<commit> ｜ 位置：<worktree 或 主项目>

## 目标
- 要做到：<可观察的结果>
- 不做：<非目标>
- 来源：用户确认 / 默认假设（可推翻）/ 待用户确认

## 范围
- 改：<文件或模块>
- 不碰：<文件或模块>

## 完成标准
- [ ] <标准> —— 验证：<命令或检查>
- [ ] 需要用户看的：<无 / 看什么>

## 记录
<!-- 只写要点：命令 → 结果 → 结论。长日志、长表格放文件，这里给路径 -->
- 验证：
- 审查：
- 验收：
- 合并：
- 风险 / 遗留：
```

- 做的过程中范围变了：改"范围"一段，写一句原因。变化大到像是另一个任务，就拆一个新 TASK。
- 标为"待用户确认"的内容不能当作完成标准，要等确认后才算。

## 4. 并行

几个任务同时做时，每个任务都要有自己的 TASK、分支和 worktree。如果会碰到同一批文件，在 TASK 里写清楚是哪几个任务、预计谁先合并。

# 复盘

每完成一批工作，都应该让下一批更容易。复盘每天做一次，看的是**合进去的东西**，而不是某一项的过程。

适用于：用户说"复盘""今天怎么样"；定时任务触发；或者当天有合并、但还没复盘就要结束工作。

## 1. 定时

- 建议每晚跑一次。设置定时任务（`/schedule`、`/loop`、桌面应用的计划任务）属于持久配置，第一次要用户同意；同意后写进项目 `AGENTS.md`。
- 没有定时任务时，在当天最后一次汇报前做一次。

## 2. 每晚复盘

1. 读 `LESSONS.md` 头部的 `reviewed-through: <sha>`，列出从那以后合进主干的全部提交。
2. 在主干上跑 verify:full（没有 CI 的项目以这次为准）。
3. 逐个提交找三类问题：
   - **返工了的**：后面有提交在"修复"一行指向它，或者它被 revert 了；
   - **不该合的**：不在目标范围内、违反已有标准、本该是单向门却自走了；
   - **验证太薄的**：提交正文没有"跑了"或"改坏验证"；没有被任何一条 Pass note 的"覆盖"范围包含（纯文档除外；一项改动拆成几个提交时，note 只挂在最后一个上，前面的提交由它的覆盖范围算进去）；或者写的验证证明不了声称的结果。
4. 每个问题写成一条教训，写进 `LESSONS.md`：

```
## <规则，一句话>
原因：<为什么>
证据：<提交 sha 列表>
Seen：<不同日期的数量>（<日期列表>）
```

   已有同一条的，更新证据，日期是新的就给 Seen 加一。
5. **升级**：Seen 达到 3 的教训，从 `LESSONS.md` 移走，改成更硬的形态。按这个顺序选第一个做得到的：
   1. 架构或类型：让错误写法写不出来
   2. lint、测试、hook：让它自动报错
   3. `docs/code-standards.md` 里的一条：验证方逐条按它查
   升级本身是一项自走档的改动，照常证明、验证、合并。
6. 更新 `reviewed-through` 为本次看到的最新提交。
7. 更新北极星数字（口径见项目 `AGENTS.md`）。

## 3. 每日摘要

复盘完给用户写一份，白话，控制在一屏以内：

```
今天：合了 N 项（列出每项一句结果）
北极星：<数字>（昨天 <数字>）
返工：<返工的项数> / <合并的项数>；被你打回：<数> / <批次里的项数>
新教训：<一句一条>；升级了：<哪条变成了什么>
待清理：<已合并但还没删的分支和 worktree 个数；0 就写"无">
审批：<今天弹了几次权限审批，主要卡在哪类操作；没有就写"无">
要你做：<无 / 待看的、待授权的、待决定的>
建议：<无 / 信任等级升或降，附两周的数据>
```

"要你做"不凭记忆写：队列里状态是"待用户"的项逐条列出，一项一行，白话写要用户决定或看什么，附推荐答案；看一眼档附上能直接打开的截图或样例输出。分支名、sha、命令不写进来，用户问了再答。

信任等级只能建议，由用户在 `AGENTS.md` 里改。

## 4. 每周清理

交给便宜的模型做，照常走验证和合并：

- 删死代码和不再用的脚本。
- 对照代码校正 `docs/feature-map.md` 和子系统文档。
- 精简 `AGENTS.md`，保持 100 行以内的目录；长内容移到 `docs/`。
- 状态类文档（进度、现状）压到一页以内的白话；sha 和长日志只留在提交正文和证据目录里。
- 整理队列：关掉过时的项，合并重复的项。
- 盘点分支和 worktree：列出已经合进主干、没有未提交改动的。项目 `AGENTS.md` 授权了自动清理的就删；没有授权的，一次性列给用户批。没合并的或有未提交改动的，只列出来说明情况，不动。

## 5. 不留的

- 聊天全文、一次性的状态、没验证过的猜测
- 密钥、账号、本机绝对路径
- 提交正文里已经写过的内容

## 6. 规则本身的维护

某条规则（包括这个 skill 里的）拖慢了工作，却从来没防住过问题；或者两处规则互相矛盾：在每日摘要的"建议"里提一句删改建议，由用户决定。

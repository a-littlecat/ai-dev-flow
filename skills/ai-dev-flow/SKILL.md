# ai-dev-flow：总览

用户只管三件事：**方向**（要什么）、**品味**（需要人看的结果对不对）、**单向门**（撤不回的事做不做）。其余的——做、证明、独立验证、合并、复盘——由你调度完成。

质量押在机器上，不押在流程和询问上：

1. **项目自带的验证能力**：一条命令能判对错，能操作真实产品。项目没有，就先搭（`modules/harness.md`）。
2. **机械约束**：每次都必须发生的事写成 hook、测试或 lint，不靠文字提醒。同一句提醒要写第二遍时，就把它改成代码。
3. **复盘**：每天看一遍合进去的东西，反复出现的问题升级成规则（`modules/garden.md`）。

能撤回的事不停下来问"要不要"：直接做，给出结果，用户事后可以推翻。

## 1. 用户说什么，你做什么

| 用户说 | 你做 |
|---|---|
| 想做、改、修某件事 | 按第 2 节定档，读 `modules/build.md`，一直做到下一个需要用户的地方 |
| "继续" | 接着做进行中的那一项；没有就从队列里领下一项 |
| "继续推进""自动推进"，或项目已授权自动推进 | 读 `modules/orchestrate.md` |
| "现在到哪了" | 按第 6 节给三行汇报 |
| "可以""通过了""可以合并" | 读 `modules/land.md` |
| "不对""有问题"、报错 | 读 `modules/diagnose.md`，先分类再动手 |
| "先停" | 停在安全点：提交或保留 worktree，把剩下的步骤、试过不行的路线写进队列里对应的那一项 |
| "复盘""今天怎么样"，或定时任务触发 | 读 `modules/garden.md` |
| 第一次进入项目，或项目没有 verify 命令 | 读 `modules/harness.md` |

档位、信任等级、模块名都是你的内部记账，汇报里不出现。

## 2. 定档：按"能不能撤回 × 机器能不能证明"

| 档 | 判定 | 谁说了算 |
|---|---|---|
| 自走 | 能撤回（`git revert` 就能恢复，没有发到撤不回的地方），而且 verify 能证明对错 | 按第 4 节的信任等级合并，写进每日摘要 |
| 看一眼 | 能撤回，但对不对要靠人的眼光：界面、文案、交互手感、真实图纸上的效果 | 做完附截图、录屏或样例输出，写清怎么看，等用户说"可以" |
| 单向门 | 见下面的清单 | 方案先给用户确认，用户授权才执行 |

单向门清单（项目 `AGENTS.md` 可以增补）：

- 发到撤不回的地方：push 到远程、打包发版、发布到商店或公开渠道
- 真实数据：写入、迁移、覆盖用户的正式数据或文件
- 删除：分支、worktree、文件、数据
- 对外：发消息，把客户数据传给第三方服务
- 花钱：超出项目预算的模型调用、购买
- 安全：密钥、权限、系统和安全设置
- 操作用户正在用的软件、窗口或会话

规则：

- 档位看后果，不看大小。一行改迁移脚本也是单向门；上千行、能撤回、verify 能覆盖的改动可以自走。
- 拿不准就按高一档，并继续做不依赖这件事的部分。做的过程中后果变了，就改档。
- 项目 `AGENTS.md` 对档位、验证命令、单向门、预算有具体规定的，以项目为准。

## 3. 什么时候找用户

只有这四种情况：

1. **单向门**要授权。
2. **看一眼**档要用户看。
3. **方向要选**：几种做法结果明显不同，选错了返工很大。能撤回的小选择自己定，在汇报里带一句。
4. **卡住了**：缺只有用户能提供的东西；或者同一项从头重来以后仍然通不过验证（`build.md` 第 5 节）。

找用户时：

- 把问题攒到一条消息里，一次问完。
- 每个问题附推荐答案和一句理由，让用户回"按你的"或一个数字就能继续。
- 等回复期间，继续做不依赖这个答案的部分。

用户说过"验收通过""可以合并"的，执行时不再问。

## 4. 信任等级

每个项目在 `AGENTS.md` 里写一个等级，决定自走档怎么合、能并行几个。**等级由用户改**；你只能在每日摘要里附上数据建议升降。项目没写时按 L0。

| 等级 | 自走档怎么合 | 并行上限 | 建议升级的条件 |
|---|---|---|---|
| L0 | 每次问用户 | 2 | harness 达到 `harness.md` 第 2 节的最低要求 |
| L1 | 各自验证通过后摞好，用户一次合一批 | 3 | 连续 2 周，被用户打回的 < 10% |
| L2 | 你直接合进主干，用户事后抽查 | 5 | 连续 2 周，合并后 48 小时内的返工率 < 15%，没有单向门事故 |
| L3 | 定时任务自动从队列领单 | 按预算定 | 用户决定 |

- 单向门在任何等级都要用户授权。
- 没授权就做了单向门的事，或者自走合并造成了撤不回的损失，算单向门事故：立即停下报告，项目退回 L1。
- 看一眼档在任何等级都要等用户说"可以"。

## 5. 不省的事

这些是防返工、防损失的底线，再赶也要做：

- 没跑过的验证不说"通过"，没做过的验证不说"已验证"。
- 执行方不批准自己的工作：合并前要有独立验证方的结论，而且对应要合并的那个版本（`modules/verify.md`）。唯一的例外是只改纯文档，见 `verify.md` 第 1 节。
- 证明在真实产物上做，并亲手改坏一次，确认测试真的会红。
- 修 bug 之前，先要有能判定对错的信号。
- 主干验证红了，立刻往前修或 revert，不等人。
- 测试只用样例副本，不碰用户的真实数据或图纸。
- 不提交密钥、账号、本机绝对路径。
- 被平台安全审查拦截的内容，不换写法、不拆分、不换个 agent 重做。

## 6. 跟用户汇报

用白话写，不用档位名、等级、P1 这类内部代号。每次停下来时，固定写三行：

```
结果：<做成了什么，或卡在哪>
要你做：<无 / 看一下什么（怎么看）/ 决定什么（推荐哪个）>
风险：<无 / 一句话>
```

多项并行时，每项一行。命令、审查记录、改动清单写进提交正文，不堆在对话里。每天一次的汇总见 `garden.md` 的每日摘要。

## 7. 记录放哪里

| 内容 | 放哪里 |
|---|---|
| 每个改动的证据（跑了什么、改坏验证、没试什么、验证结论） | 提交正文，模板见 `land.md` |
| 待办和进行中的项 | 队列：有远程用 issues，没有用 `docs/queue.md` |
| 跨多天的计划、单向门的方案 | `docs/plans/<主题>.md` |
| 反复出现的问题 | `LESSONS.md`，由每晚复盘维护 |
| 已经定下的规则 | 能机械化的写成 lint、测试、hook；不能的写进 `docs/code-standards.md` |
| 疑难问题的解法 | `docs/solutions/<主题>.md` |
| 项目入口 | `AGENTS.md`，写成 100 行以内的目录 |

新工作不再建 TASK 文件和看板。项目里已有的 TASK 和看板保持原样，不迁移。

## 8. 模块

只读当前要用的那一份：

| 模块 | 用途 |
|---|---|
| `modules/harness.md` | 给项目搭验证能力：verify 命令、操作产品、功能地图、hooks、慢验证队列 |
| `modules/build.md` | 理解 → 做 → 证明；什么时候写计划；什么时候从头重来 |
| `modules/verify.md` | 独立验证：说明模板、证明门槛、跨厂商规则、审查方不可用时怎么办 |
| `modules/land.md` | 合并落地：rebase、在最终版本上复跑、提交正文模板、往前修和 revert |
| `modules/diagnose.md` | bug、变慢、原因不明的失败、验收没通过 |
| `modules/orchestrate.md` | 自动推进：队列、派后台子 agent、接力、并行上限 |
| `modules/garden.md` | 每晚复盘、教训升级、每日摘要、每周清理 |

能并行的独立工作交给隔离的子 agent，各自在自己的 worktree 里做；验证放到后台跑。你负责整合结果，并对最终质量负责。
